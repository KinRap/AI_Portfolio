TaskFlow
Agentic Analytics

A six-agent LLM pipeline that answers "why is MRR growth slowing?" for a SaaS business. What sets it apart is the measurement: a deterministic SQL audit layer benchmarks each agent's accuracy on recall and precision, instead of judging the system by impression.

The problem

Boardroom questions are vague on purpose. "Why is MRR growth slowing?" has no single answer: it could be rising churn, weaker acquisition, downgrades, or a cohort that stopped expanding. Answering it means decomposing the question, writing correct SQL against messy production data, interpreting the result, and turning it into a recommendation a leader can act on.

But there is a deeper problem most LLM analytics demos ignore: can you trust the data, and can you trust the agent? Real SaaS data is dirty (negative MRR, duplicate invoices, orphaned records, inconsistent formats). An agent that confidently answers on broken data is worse than no agent at all. TaskFlow was built to handle both: produce the analysis, and measure how reliably it does so.

Architecture - six-agent pipeline

Each agent has a single responsibility, its own temperature, and a structured JSON output that becomes the next agent's input. Running alongside the agents is a deterministic SQL audit layer (plain code, 16 checks) that serves as ground truth for evaluation.

1
DQA - Data Quality Agent
Audits the data with the suspicion of a good auditor. Triages anomalies by severity, builds a trust report per table and column. Reads raw statistics (min/max, distributions, sample rows), not pre computed answers, so it has to detect issues itself. Temperature 0.15.
Output: triage + trust report + discovery
↓
2
ANA - Analyst
Decomposes the vague question into 2 to 6 answerable sub-questions. Enforces a churn duet (logo churn and revenue churn as separate metrics) and flags cohort metrics like NRR that require a self join. Does not write SQL. Temperature 0.2.
Output: analytical plan + assumptions
↓   repair loop ↓
3
SQG - SQL Generator
The sole author of SQL. Writes one read-only query per sub-question, returning absolute values alongside ratios so the interpreter knows the scale. Handles recursive month series and self joins for cohort analysis. Temperature 0.0.
Output: one SELECT / WITH query
4
VAL - Validator
A skeptical reviewer that checks SQL before execution. Never writes SQL itself: it reports assertions, and SQG regenerates. Deliberately tuned to be strict, because in a data quality system an over cautious gate is safer than a permissive one. Temperature 0.1.
Output: verdict OK / FIX + error assertions
↓
5
INT - Interpreter
A data translator, not a strategist. Describes what the numbers show in absolute terms and identifies patterns. Forbidden from stating causes or recommendations: that boundary keeps the diagnosis honest and traceable. Temperature 0.3.
Output: observations + pattern + data caveats
↓
6
ADV - Advisor
The only agent allowed to state causes. Diagnoses why, gives exactly one measurable recommendation, and calibrates its confidence to data quality: when the trust report is full of problems, it lowers confidence and recommends fixing the data first.
Output: diagnosis + recommendation + confidence

Key technical decisions

A deterministic audit as ground truth

The hardest part of evaluating an LLM is knowing the right answer. Here, a plain SQL audit layer computes the real anomalies independently, so the data quality agent's output can be scored on recall and precision against it. This turns "the agent seems good" into "the agent caught 11 of 14 categories with zero false positives".

Single author repair loop

Only SQG writes SQL. VAL reviews and reports assertions, SQG regenerates. One author, one reviewer. This avoids the failure mode where two agents fight over the same code, and it makes the repair loop observable in the audit trace.

Honest discovery, not list matching

Two anomaly types were deliberately left out of the agent's rules. If it finds them, that is reasoning. In practice the agent reached the concept (activity after churn) but described it as one holistic point rather than two separate measurable detections. The score reflects that honestly: the model has intuition but does not yet operationalize it.

A deliberately strict validator

VAL sometimes rejects correct SQL. That was a design choice, not a bug: in a data quality system, an over cautious gate that occasionally asks for a second look is safer than a permissive one that lets a flawed query reach production.

Safety from the start

The executor accepts read-only queries only, guarded by a regex that rejects any data modifying statement. The model call has a timeout and retry with backoff, so a hanging connection fails cleanly instead of blocking forever. The API key is read from Colab Secrets, never hardcoded.

Reproducible by design

The database is generated from a seeded script, not committed as a binary. A startup cell pulls the generator from this repo and rebuilds the data, so the notebook runs from zero on any machine, for anyone, without local files.

What's next

The pipeline is built, measured, and documented. Natural next steps: extend the evaluation harness to score the SQL generator and advisor as systematically as the data quality agent, add a results dashboard rendered directly from each run, and migrate the model client to the newer google.genai SDK. The methodology, not just the code, is the deliverable here.
